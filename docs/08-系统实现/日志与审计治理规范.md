# 日志与审计治理规范

## 1. 目标与边界

本规范覆盖九个子系统。运行日志用于定位故障，数据库审计记录用于追溯业务变更，两者不能互相替代。系统必须能回答：谁在什么时间执行了什么操作、结果是什么；一次请求或消息经过哪些步骤；异常发生在哪个服务、入口和业务标识；RocketMQ 消息是否生产、消费或进入重试。

禁止记录密码、Access Token、Authorization/Cookie、Nacos/Redis/RocketMQ/MySQL 密钥、完整请求体、完整响应体和非必要个人信息。日志仅使用字段白名单，不通过 `toString()` 输出命令对象。

## 2. 统一格式

```text
time=2026-08-08T14:30:00.000+08:00 level=INFO service=purchase-service thread=http-nio-8102-exec-1 traceId=... requestId=... operatorId=1001 operator=zhangsan logger=... message=event=http_request_completed operation=POST /api/purchase/v1/orders result=SUCCESS status=200 durationMs=35
```

| 字段 | 规则 |
| --- | --- |
| `time` | ISO-8601，包含毫秒和时区；由日志框架生成，不能由业务端伪造 |
| `service` | `spring.application.name` |
| `traceId/requestId` | 接受符合安全字符规则的上游值，否则生成 UUID；响应头原样回传安全值 |
| `operatorId/operator` | JWT 访问上下文；MQ、定时任务固定为 `0/system` |
| `event` | 稳定事件名，如 `http_request_completed`、`rocketmq_publish`、`rocketmq_consume`、`batch_task` |
| `operation` | 稳定操作名或 HTTP 方法与路径，不包含查询参数 |
| `result` | `SUCCESS`、`REJECTED`、`RETRY`、`FAILURE` |
| `status/durationMs` | HTTP 状态码和操作耗时；适用时记录 |

## 3. 级别与覆盖

| 级别 | 使用场景 | 文件 |
| --- | --- | --- |
| `INFO` | 业务操作成功、RocketMQ 生产/消费成功、批处理成功 | `logs/<service>/info/info.log` |
| `WARN` | 可自动恢复的拒绝、重复消息、Broker 将重投的消费失败 | `logs/<service>/info/info.log` |
| `ERROR` | 未处理异常、HTTP 5xx、消息生产失败、导出/集成命令失败、补偿记录失败 | `logs/<service>/error/error.log` |

九个服务的 HTTP 请求均由公共安全链自动记录。RocketMQ 的 11 个真实消费入口记录成功和重试；九个 Outbox 发布服务记录发布成功和带堆栈的失败；库存、OMS、供应商、MDM 导出/文件任务及采购、供应商跨系统命令记录任务结果。高频 Outbox 空轮询不写成功日志，避免无业务事实的日志洪泛；实际消息发布逐条记录。

业务状态修改仍应在所属限界上下文的审计表保存操作人、业务对象、前后状态/版本、原因、结果和发生时间。文件日志故障不应回滚已经满足业务不变量的数据库事务，数据库审计写入失败则必须按所在事务失败关闭。

## 4. 滚动、保留与容量

每个服务、每个级别目录独立滚动：跨天或当前文件达到大小上限即生成 `*.yyyy-MM-dd.<序号>.log.gz`。

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `scm.logging.path` | `./logs` | 日志根目录 |
| `scm.logging.max-file-size` | `100MB` | 单个 INFO 或 ERROR 文件最大值 |
| `scm.logging.max-history` | `7` | 保留七个按日周期，超过七天自动删除 |
| `scm.logging.info-total-size-cap` | `2GB` | 单服务 INFO/WARN 历史文件总上限 |
| `scm.logging.error-total-size-cap` | `1GB` | 单服务 ERROR 历史文件总上限 |

时间和容量规则同时生效，先达到任一上限即清理；应用启动时也执行历史清理。以上键已发布到 `scm-common-{env}.yaml`，test/prod 可在 Nacos 分别覆盖，修改后重启服务使 Logback 完整重载。容器环境应把 `scm.logging.path` 指向持久卷；磁盘告警阈值仍由生产监控配置。

## 5. 异常定位流程

1. 从响应头取得 `X-Request-Id`、`X-Trace-Id`，或从 RocketMQ `messageId/eventId` 开始查询。
2. 先查当前服务 `error/error.log`，再按同一 `traceId/requestId` 串联 `info/info.log`。
3. 对消息问题核对 `rocketmq_publish` 与 `rocketmq_consume`，再核对 Outbox/Inbox 状态、重试次数和失败原因。
4. 对业务争议以数据库审计表为准，文件日志用于补充运行堆栈，不以日志文本反向修改业务事实。
5. 排障导出日志时只共享必要片段，继续执行凭据与个人信息脱敏。

## 6. 自动门禁

执行 `project/qa/test-logging-governance.sh`，检查九个服务配置、INFO/ERROR 分流、日期+大小滚动、七天清理、总容量、HTTP 审计、11 个 RocketMQ 消费入口和敏感字段禁写规则。
